1. The big picture

A software factory is a pipeline where agents write the code and decide whether it merges. Humans own the intent (specs, scenarios), the harness, and the risk policy. Generating code is not the hard part. Trusting code nobody read is. Every serious practitioner lands on the same answer: verification by something other than the author, against an oracle the author cannot edit, producing evidence instead of claims.

The autonomy spectrum

You don't pick one point on this line. You pick it per risk tier (section 6). Everyone keeps humans on auth, billing, migrations and other one-way doors. HumanLayer turned review back on after an outage in code nobody had read for three months.

Matt Pocock: day shift / night shift

The human grills, approves test seams and tickets, then QAs and merges. The AFK loop (sandcastle) runs sandboxed, can't push, and always ends in a PR. He treats a dark factory as a failure mode.

Lauren Tan: trust before parallelism

1–5 supervised agents until they can check their own work. A per-app verification skill is critical infrastructure. The overnight run is a contract. Only verified patches self-merge. She reviews main in the morning, not every PR.

StrongDM: dark factory

"Specs + scenarios drive agents that write code, run harnesses, and converge without human review." Holdout scenarios live outside the repo; digital twins stand in for third-party services.

Your chosen destination (R3): Tan-style for low-risk tiers (verifiers merge, you audit main), Pocock-style (you merge) for everything else. Never a dark factory. Shapiro's level 3 to 4 jump is not about better models; it is about replacing your diff review with verification you trust more than your own skim of the diff.

Where they conflict

Human at merge vs self-merge

Pocock and ADW: human. Poteto (Autopilot-full) and StrongDM: agent. Self-merge fits a trusted verifier, reversible changes, cheap revert. Human merge fits one-way doors and thin test suites. Resolved per risk tier.

TDD required vs not

Pocock's skills require it (though he has since moved away from requiring it). Poteto uses it when the test is cheap. StrongDM moves the oracle out of the repo. TDD pays where seams are clean; a run-the-app verifier catches more where the risk is wiring or startup.

Memory vault vs codebase-as-memory

Poteto dropped her vault: "your codebase is the ultimate form of memory". Lessons become lint, types and skills. Check whether a note could be a check first.

Rubric axes vs model diversity

Pocock: two axes. pstack: "adversarial signal comes from model diversity, not personas". Orthogonal, so use both; in Claude Code diversity collapses to Opus vs Sonnet.

Self-declared done vs independent verifier

Ralph and sandcastle trust a promise tag. pstack, Anthropic and StrongDM do not. Once no human reads the diff, the done signal must come from something the author cannot write.

Resolve ambiguity before vs during

Pocock grills until the frontier is empty ("coherent about the wrong thing" is the AFK failure). pstack settles empirical forks by prototype mid-run and parks the rest with defaults.

Who picks the next task

The agent (Ralph), a planner agent (sandcastle), a script over a dependency graph (orchestrate), or a human (ADW). A deterministic frontier suits parallel work.

Worktrees vs sandboxes vs cloud VMs; draft vs ready PRs; auto vs approved learning

Worktrees are cheapest but share credentials. Containers add an egress boundary; VMs survive a closed laptop. Draft PRs suit human-merge; ready-plus-verdict suits verifier-gated merge. Anything that changes future agents' behavior needs approval or an eval.

Where they all agree

  1. The writer never grades itself.
  2. Verification is the bottleneck, not generation.
  3. Run the real thing.
  4. State lives on disk and in git, not in the chat.
  5. One unit of work per fresh context.
  6. Deterministic work goes in code; judgment goes to the model.
  7. Encode lessons as structure ("the instruction is the symptom").
  8. Hard stops exist. "A duration is not a finish condition."
  9. Irreversible actions stay human.
  10. Earn trust before scaling out.
  11. Humans keep the spec and the risk policy.

5. Verification deep dive

The vocabulary (settled in R6; "validation" is retired)

Check

A deterministic gate (types, lint, tests, static analysis) whose pass/fail the implementing agent cannot edit.

Verification

An agent that did not write the change runs the real application against claims fixed before the run and records evidence.

Claim

One observable statement about the running app with an explicit expected observation, fixed before verification starts.

Verdict

The outcome of one verification, bound to the exact code it judged, with evidence attached.

Review

An agent or human reads the diff for quality and fit to the spec, without running the app.

Author vs Verifier

Where this repo already leads: verify is the only skill of the three that makes the oracle read-only by mechanism (a fail-closed PreToolUse guard on the verifier agent), not by instruction. pstack enforces nothing mechanically; Pocock has no run-the-app verifier at all.

The gaps (prioritized in the skills comparison):

  1. ship-gate never reads the verify verdict, so a branch can ship with no report or a FAIL.
  2. The author writes the claims. The one real run passed "GET /health answers" while the body said "status": "unhealthy". Vague expectations should make a run INCONCLUSIVE.
  3. No project recipe: every run rediscovers launch, port and seed data.
  4. Nothing proves the verifier can fail (no parent-SHA "must fail" run, no planted failure).
  5. The running app must match the commit under test; degraded dependencies mean INCONCLUSIVE, not PASS.

The verification ladder

Not all "verified" is equal. The orchestrate plugin stores the strongest rung the evidence supports on the target task, overriding the worker's self-report. pstack's ledger uses the same values.

  • live-ui-verifiedReproduced live (real browser, binary or CLI); the fix removes it. Trust as shipped.
  • unit-test-verifiedA targeted test exercises the changed path. OK for non-UI; UI bugs want a live pass later.
  • type-check-onlyOnly build or type-check passed. Weak; only for typing-only changes.
  • verifier-blockedEnvironment failure prevented the check. "Don't count as verified." Respawn when healthy.
  • verifier-failedRan it; the fix did not work. Follow-up fix task.
  • not-verifiedSelf-report only.

Anti-laundering rule: "Don't report type-check-only for a check you didn't run end-to-end; that disguises an env failure." pstack per-run verdicts: VERIFIED / NOT VERIFIED / INCONCLUSIVE, and "inconclusive is not a pass". /pstack:blast-radius has its own five-step proof ladder that ends at "you ran it" and "you reproduced it in the running app".

The proof bar (what counts as evidence)
  1. Real user path, not internal setters or test-only endpoints. No "look, it opens" captures.
  2. Capture the action and the resulting state in the same recording.
  3. Side effects read back (files written, rows inserted) through a second, read-only view.
  4. Mocks only behind an existing production boundary.
  5. Dry-run is observed, not trusted: some dry-runs still touch the network.
  6. Fresh build: "a video against a stale bundle is not evidence".
  7. The coverage set is the feature file: every entry point, mode, success / cancel / error / empty / persistence path the change can affect.
  8. Per-surface minimums: UI = ARIA snapshot + screenshot with app identity; CLI = command, stdout, stderr, exit code.
  9. Honest skips: report the attempted command and unmet precondition; never claim a skipped path via another one.

The recipe generator idea: protocol vs recipe

verify = the protocol (keep)

Who grades, what is read-only (the guard), the claim rules, the report schema, verdict rules. Generic across every stack.

verify-<app> = the recipe (generate per repo)

How to Launch, Doctor, Drive, Evidence, Cleanup this app, plus a features/ map. Generated by pstack's /pstack:create-verification-skill (or a proposed create-verify-recipe), proven once end to end before it counts, kept honest by /pstack:maintain-verification-skill.

Proposed create-verify-recipe output (target repo, committed) 
.claude/skills/verify-<app>/
  SKILL.md      # Launch, Doctor, Drive, Evidence, Cleanup, Helpers, Feature map
  recipe.json   # machine-readable subset read by verify and pipelines
  bin/          # launch, doctor, cleanup (+ optional ctl)
  probes/       # Hurl / Playwright / CLI drive scripts per feature (read-only to authors)
  features/
    README.md   # baseline preconditions, conventions, proof + skip rules, status table
    <feature>.md

The generator is an author; its proof run is a verifier dispatch, so the read-only guard needs no change. Maintenance outcomes: clean (no PR), changed (one PR of proven map/harness fixes), or blocked. "A feature map rots the moment the app changes." Never edits product code.

Binding a verdict to the code: git patch-id

base=$(git merge-base origin/main HEAD)        # stacked PR: the parent branch tip
git diff --binary "$base" HEAD | git patch-id --verbatim | cut -d' ' -f1

Keeps the verdict

  • Rebase over unrelated trunk commits
  • Trunk touched the same file outside the 3-line context
  • Squashing, re-splitting or rewording commits
  • Clean retarget of a stacked child after its parent merged

Invalidates the verdict

  • Any change to an added or removed line
  • Any new or deleted file in the PR
  • Trunk changing a line inside the patch's context window
  • Conflict resolution; whitespace change under --verbatim

The --verbatim finding. The default and --stable modes ignore whitespace. In Python, moving return 3 into an if block changes behavior, yet both versions hash the same under --stable and differently under --verbatim. pstack's Shipping playbook names no mode. Use --verbatim everywhere (YAML, Python, Makefiles, application.yml) as one rule. An empty diff gives an empty ID, so the check must fail closed.

What patch-id cannot see: trunk changing code the patch calls in another file. Same ID, different behavior. Autopilot-full re-runs the patch's checks on the merge result in that case. Patch-id is necessary for carrying a verdict, not sufficient.

The verdict-outside-the-agent rule still needs one deterministic component the agent can't influence: a Stop/SubagentStop hook that runs the checks, an Action, or the thin driver. Not a whole harness.

Model diversity collapses: in Claude Code, "different family" verification means Opus vs Sonnet unless you bridge to another vendor (R5 keeps it Claude-only for now).

10. Glossary

Canonical terms (from GLOSSARY.md)

TermMeaningAvoid
CheckA deterministic gate (types, lint, tests, static analysis) whose pass/fail the implementing agent cannot edit.Gate (alone), validation
VerificationAn agent that did not write the change runs the real application against claims fixed before the run and records evidence.Validation, testing, QA
VerdictThe outcome of one verification, bound to the exact code it judged, with evidence attached.Result, report, sign-off
ClaimOne observable statement about the running application with an explicit expected observation, fixed before verification starts.Assertion, test case, acceptance criterion
ReviewAn agent or human reads the diff for quality and fit to the spec, without running the application.Verification, code check
AuthorThe agent that wrote the change. It never produces the Verdict on its own work.Worker, implementer, owner
VerifierThe agent that runs the application and produces the Verdict, with no write access to the code or the claims.Grader, judge, tester

Other terms used in this guide

TermMeaning
Software factoryA setup where agents write the code and also decide whether it merges; humans own intent, harness and risk policy.
Dark factoryThe extreme: no human reads the code or the review. Pocock treats it as a failure mode; you ruled it out (R3).
AFK / HITLAway-from-keyboard vs human-in-the-loop. Pocock encodes the split as ready-for-agent vs ready-for-human labels.
Done predicateA falsifiable condition re-checked every iteration. "A duration is not a finish condition."
Control CLI / control skillA small per-app tool that boots and drives the real app (CDP, Playwright, tmux), with a doctor check.
Feature mapA per-app list of user flows and how to prove each; the standing oracle for regressions. "Materialized memory."
Protocol vs recipeProtocol: who grades, what is read-only, verdict format (verify). Recipe: how to run this app (verify-<app>).
Live laneThe verifier lane that drives the running app. pstack: no clean verdict without it.
SwarmN parallel fresh workers or verifiers with a selection rule declared before spawning.
git patch-idA hash of a diff ignoring line numbers and commit metadata; lets a verdict survive a clean rebase but not a code change. Use --verbatim.
Decision logdecisions.tsv (ts, phase, decision, why, evidence, result), one row per iteration, audited in the morning.
gates.mdParked questions for the human, each with a "default on no answer", so the run never blocks.
FrontierThe set of work (or decisions) whose prerequisites are settled: unblocked tickets, or the next grilling questions.
Tracer-bullet sliceA narrow but complete path through every layer, sized to one fresh context window.
Holdout scenarios / digital twinsStrongDM: tests kept outside the repo so agents can't edit them; fake third-party services to run them against.
One-way / two-way doorIrreversible vs cheaply reversible change. One-way doors stay human (T3).
BackpressureRalph's term for checks (types, tests, scanners) that push back on the loop. Pocock avoids the word because it lumps checks with review.
